# HELPER DEFS (deck lines 197-237) -- offgrid_cl / ongrid_ep definitions required by AUX rules
  def offgrid_cl(axis, pitch_dbu, offset_dbu, base_dbu = nil)
    new_data = RBA::Region::new
    self.data.each do |p|
      bb = p.bbox
      if base_dbu
        if axis == :y
          next if bb.bottom % base_dbu != 0 || bb.top % base_dbu != 0
        else
          next if bb.left % base_dbu != 0 || bb.right % base_dbu != 0
        end
      end
      cl = axis == :y ? (bb.bottom + bb.top) / 2 : (bb.left + bb.right) / 2
      if (cl - offset_dbu) % pitch_dbu != 0
        if axis == :y
          new_data.insert(p.moved(0, cl - bb.bottom))
        else
          new_data.insert(p.moved(cl - bb.left, 0))
        end
      end
    end
    DRC::DRCLayer::new(@engine, new_data)
  end

  def ongrid_ep(gx_dbu, gy_dbu)
    result = RBA::EdgePairs::new
    self.data.each do |poly|
      pts = poly.each_point_hull.to_a
      pts.each_with_index do |pt, idx|
        offgrid_x = (gx_dbu > 1) && (pt.x % gx_dbu != 0)
        offgrid_y = (gy_dbu > 1) && (pt.y % gy_dbu != 0)
        if offgrid_x || offgrid_y
          pp = pts[(idx - 1) % pts.size]
          np = pts[(idx + 1) % pts.size]
          e1 = RBA::Edge::new(pp, pt)
          e2 = RBA::Edge::new(pt, np)
          result.insert(RBA::EdgePair::new(e1, e2))
        end
      end
    end
    DRC::DRCLayer::new(@engine, result)
  end

## Per-rule recipes

### Family C: M5 off-grid vertical edges (M5.AUX.1)

Rule semantics: M5.AUX.1 enforces that all M5 vertical edge x-coordinates sit on the 24 nm = 96 dbu grid. M5.AUX.2 (latent partner) additionally enforces that minimum-width M5 track centerlines satisfy center_x mod 192 == 48. The deck evaluates M5.AUX.2 only for polygons whose x-edges already pass M5.AUX.1; a polygon failing M5.AUX.1 is skipped by M5.AUX.2, so the track constraint is dormant and a wrong-phase x-shift can surface it as a new violation. This double-grid structure parallels M4 Family B (-> see M4.md / V3.md).

Root cause pattern (seed, reference-design-verified): both changed M5 polygons (96 dbu wide = minimum width) had x_left at residual 88 both mod 96 and mod 192. Snapping by -88 puts the edges on the 96 grid AND the centerline on a legal track (center_x mod 192 == 48). Snapping by +8 also fixes M5.AUX.1 but lands the centerline at 144 mod 192 -- an illegal track that surfaces the dormant M5.AUX.2. The full-deck legal positions repeat every 192 dbu; the nearest candidates were -88 and +104, and -88 is the smaller.

Recipe -- Uniform x-shift (seed, reference-design-verified): Compute the TRACK residual r = x_left mod 192 (in dbu). For a minimum-width (96 dbu) stripe, legal positions are x_left == 0 mod 192, satisfying both M5.AUX.1 (edges on 96 grid) and M5.AUX.2 (centerline at center_x mod 192 == 48). The two nearest legal candidates are delta_x = -r and delta_x = +(192 - r); take the smaller magnitude. In the reference pair, r == 88 for both stripes, giving delta_x = -88 (+104 is legal but larger; a plain mod-96 delta of +8 is not legal -- it lands the centerline at the 144-phase track, an illegal routing track). A stripe in the other phase (r == 184) takes +8 instead. Shift the M5 polygon by delta_x in x with y unchanged. Apply the same delta_x to every associated VIA_VIA45 instance to keep V4 centered inside M5. Because the VIA45 x-position changed, verify the MERGED M4 (top-level polygon + via cell M4 land) at the new x; if no longer valid, adjust the top-level M4 x-extent as in Family B Step 3 (-> see M4.md / V3.md). Merged M4 validity is assessed on the combined geometry, not the top-level polygon alone.

Worked example C1 (seed, reference-design-verified) (M5 polygon at x=1816-1912, 2 of the 4 M5.AUX.1 violations):
  M5 BEFORE x=1816-1912. r = 1816 mod 192 = 88; edges off the 96 grid; centerline 1864 at 136 mod 192 is also off-track but dormant while M5.AUX.1 fails.
  M5 AFTER x=1728-1824. 1728=18*96, 1824=19*96; centerline 1776 = 9*192 + 48.

## Case notes

M5 and M4 are tightly coupled (seed, reference-design-verified): M5.AUX.1 drives M5 x-shift, which forces VIA45 x-move, which forces top-level M4 x-extent adjustment to keep the merged M4 valid around V4. M4.AUX.1 independently forces M4 y-move. VIA45 tracks both the x-shift (from M5.AUX.1 repair) and the y-shift (from M4.AUX.1 repair); the two components are computed separately and summed to get the combined instance delta. The reference-design examples produced combined deltas of (-88, -48) and (-88, +120) (seed, reference-design-verified).

The unit_gate channel produces repairs spanning the full range of axis combinations: pure x-shifts (trial:i02.ug.leaf_0002.01), pure y-shifts (trial:i03.ug.leaf_0001.00), bidirectional y-shifts with opposing signs across instances (trial:i03.ug.leaf_0002.01), and mixed x+y repairs where distinct object subsets carry distinct axis deltas in a single trial (trial:i04.ug.leaf_0002.01). When a unit_gate repair carries only y-deltas across all ops, there is no forced x-grid adjustment and the M5.AUX.1/M5.AUX.2 constraints remain unperturbed (trial:i03.ug.leaf_0001.00, trial:i03.ug.leaf_0002.01). When a unit_gate repair carries only an x-delta, there is no forced y-adjustment to the coupled VIA45 stack (trial:i02.ug.leaf_0002.01). When both axes appear in the same trial, the x-group and y-group operate on non-overlapping instance sets and are committed together (trial:i04.ug.leaf_0002.01).
