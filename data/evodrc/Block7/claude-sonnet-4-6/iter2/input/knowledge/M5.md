  def offgrid_cl(axis, pitch_dbu, offset_dbu, base_dbu = nil)
    new_data = RBA::Region::new
    self.data.each do |p|
      bb = p.bbox
      if base_dbu
        if axis == :y
          next if bb.bottom % base_dbu != 0 || bb.top % base_dbu != 0
        else
          next if bb.left % base_dbu != 0 || bb.right % base_dbu != 0
        end
      end
      cl = axis == :y ? (bb.bottom + bb.top) / 2 : (bb.left + bb.right) / 2
      if (cl - offset_dbu) % pitch_dbu != 0
        if axis == :y
          new_data.insert(p.moved(0, cl - bb.bottom))
        else
          new_data.insert(p.moved(cl - bb.left, 0))
        end
      end
    end
    DRC::DRCLayer::new(@engine, new_data)
  end

  def ongrid_ep(gx_dbu, gy_dbu)
    result = RBA::EdgePairs::new
    self.data.each do |poly|
      pts = poly.each_point_hull.to_a
      pts.each_with_index do |pt, idx|
        offgrid_x = (gx_dbu > 1) && (pt.x % gx_dbu != 0)
        offgrid_y = (gy_dbu > 1) && (pt.y % gy_dbu != 0)
        if offgrid_x || offgrid_y
          pp = pts[(idx - 1) % pts.size]
          np = pts[(idx + 1) % pts.size]
          e1 = RBA::Edge::new(pp, pt)
          e2 = RBA::Edge::new(pt, np)
          result.insert(RBA::EdgePair::new(e1, e2))
        end
      end
    end
    DRC::DRCLayer::new(@engine, result)
  end

## Per-rule recipes

### Family C: M5 off-grid vertical edges (M5.AUX.1)

M5.AUX.1 requires M5 vertical edges (x-coordinates) to lie on the 24 nm = 96 dbu grid (seed, reference-design-verified). M5.AUX.2 (latent partner) additionally requires minimum-width M5 track centerlines at center_x mod 192 == 48. The deck evaluates M5.AUX.2 ONLY for polygons whose x-edges already sit on the 96 grid; a stripe currently failing M5.AUX.1 suppresses any M5.AUX.2 report, so a wrong-phase mod-96 snap surfaces the dormant M5.AUX.2 as a new violation. This is the same double-grid structure as M4 in Family B (seed, reference-design-verified).

Root cause pattern: both changed M5 polygons (96 dbu wide = minimum width) had x_left at residual 88 both mod 96 and mod 192. Snapping by -88 puts the edges on the 96 grid AND the centerline on a legal track (center_x mod 192 == 48). Snapping by +8 also fixes M5.AUX.1, but lands the centerline at 144 mod 192 -- an illegal track that surfaces a dormant M5.AUX.2. The full-deck legal positions repeat every 192 dbu; the nearest candidates were -88 and +104, and -88 is the smaller. A stripe in the other phase (r == 184) takes +8 instead (seed, reference-design-verified).

Recipe -- Uniform x-shift to snap M5 to grid:

Step 1. Compute the TRACK residual r = x_left mod 192 (in dbu). For a minimum-width (96 dbu) stripe the legal positions are x_left == 0 mod 192: that puts both edges on the 96 grid (M5.AUX.1) and the centerline at center_x mod 192 == 48 (M5.AUX.2). Take the smaller magnitude candidate from {-r, +(192-r)}; in the seed pair both stripes had r == 88, so delta_x = -88 (+104 is legal but larger; a plain mod-96 snap of +8 is NOT legal -- it lands the centerline on an illegal 144-phase track) (seed, reference-design-verified).

Step 2. Shift the M5 polygon by delta_x in x; y is unchanged (seed, reference-design-verified).

Step 3. For every VIA_VIA45 instance associated with this M5 polygon, apply the same delta_x to keep V4 centered inside M5 (seed, reference-design-verified).

Step 4. Because VIA45 x-position changed, check the MERGED M4 around it. Adjust the top-level M4 x-extent if the merged M4 (top-level polygon + via cell's own M4 land) is no longer valid or connected at the new x (ties to Family B Step 3). The merged M4 must contain the via; the top-level polygon alone need not satisfy that containment independently (seed, reference-design-verified).

Worked example C1 (M5 polygon at x=1816-1912, 2 of the 4 M5.AUX.1 violations) (seed, reference-design-verified):

## Case notes

M5 and M4 are tightly coupled in the whole-polygon shift recipe: M5.AUX.1 drives M5 x-shift; that shift forces VIA45 x-move; VIA45 x-move forces a top-level M4 x-extent adjustment (to keep the MERGED M4 valid around V4); M4.AUX.1 independently forces M4 y-move; VIA45 must track both x and y deltas, so compute the x and y components separately and sum them (seed, reference-design-verified).

Both can be necessary in the same design region; apply each to its target as indicated by the violation locus, as demonstrated by trial:i01.cu.def:VIA_VIA45_1_2_58_58.00 (intra-cell) alongside the seed reference-design-verified whole-polygon cases.
